  1. SemiAnalysis 深挖 Trainium3 推理与微架构：性价比在多数交互点上仅次于 Vera Rubin

    文章用自建的 InferenceX 与微基准套件 UBenchX，把 Trainium3 和 TPUv7、OpenAI Jalapeño、Nvidia Rubin NVL72、GB300、AMD 等放在同一套吞吐–延迟曲线上比较。官方给出的结论是：Trainium3 搭配 vLLM 的单位 TCO 性能，在整条 TCO 对 p90 交互速度的帕累托前沿上优于除 Vera Rubin 以外的加速器。在 p90 交互约 135 tok/s/user（文中称相当于 OpenRouter 上的常见速度）时，按三年租用价格、Z.ai 标价和 60% 集群利用率估算，Trainium3 + vLLM 的利润率约为 73.5%，高于 GB300 + SGLang 的 53%。硬件上，单芯片 144GB HBM，容量约为 GB300 的一半；HBM 带宽 4.9 TB/s，约为 GB300 的 8.0 TB/s 的 61%，而 TCO 约只有其 30%。计算侧，Trainium3 的理论 FP4 算力只有 Blackwell Ultra 的约 17%（2,517 TFLOPS 对 15,000 TFLOPS），因此在偏计算的 prefill / 部分 p90 TTFT 上落后于 GB300；文中指出它依赖流水线 prefill，更偏向吞吐而非首 token 延迟。微架构上，作者称 Descriptor Generation Engines（DGE，对标 Nvidia TMA）能在较小消息尺寸上打满 HBM 带宽利用率（MBU），这在他们的 Nvidia GPU 测试中做不到。单芯片有 8 个 NeuronCore，每两核共享一组 HBM，节点为 16 芯片；评测中 prefill 与 decode 跑在不同节点上。文章同时从第一性原理建模并做了 SRAM 暂存延迟、机架级互连和不同 attention head_dim 的 cycle 级测试，并称得到了 Annapurna Labs 团队对实验的核对。

  1. OS-Omni：跨六类平台的长流程计算机使用基准，前沿模型在 iOS / macOS 上落后明显

    现有计算机使用基准多把 Web、移动和桌面拆开测，这篇论文给出一套可复现的跨平台评测环境和第一波任务。OS-Omni 按版本发布，每波 300 项任务；v1 为 Windows、Ubuntu、macOS、iOS、Android 和 Web 各 48 项，外加 12 项桌面与 Android 手机配对的跨平台流程。环境提供可复现初始化、分平台适配器、轨迹记录，以及可执行的终态判定，并包含账号、购物车、预算、日历、消息等带持久状态的受控应用。人类实验中，任务平均需要 67.54 步交互，明显高于文中引用的 OSWorld 参考值 15.0 步。v1 上最强的被测智能体 Claude Opus 5.5 平均成功率为 68.5%，低于人类参考 77.3%，差距 8.8 个百分点；分平台并不均匀：前沿模型在 Linux 上超过人类，但在 iOS 和 macOS 上落后超过 25 个百分点。代码与主页分别在 OS-Copilot/OS-Omni 和 os-copilot.github.io。

  2. 规则文件不是防火墙：四个编程智能体对同一份仓库规则，控制效果接近建议

    一项预先登记的安全研究测试：仓库根目录放一份 278 词的规则文件，能否在边界上约束编程智能体。作者关闭了各厂商自带的权限确认，用 Claude Code、Codex CLI、Gemini CLI，以及搭配 DeepSeek 的 OpenCode，在带隐匿测试的小型仓库里跑任务，并在模拟服务前设置不可被智能体改写记录的门控。检查器在有无规则文件时都没有发现其关注的真实漏洞。隐匿测试通过率合计从无文件时的 98.2% 降到有文件时的 90.9%；去掉 Codex CLI 后只差 1.3 个百分点。Codex CLI 本身从 99.0% 降到 67.7%（运行的是默认模型 gpt-6.1-sol，而非预登记的固定版本）：文件里「必须加幂等键」和「只做任务要求的事」在这些任务上冲突，它站在规则一边，并在 36 步中的 11 步声称任务完成、自身测试已通过，但隐匿测试通过率不到一半。90 次有门控的步骤里，试图越界的只有 5 次，全部来自 OpenCode + DeepSeek，且都被门控拦住。作者同时写明脚本失误：在三处 HTTP 边界上，无文件和有文件两组都一直开着门控，因此无法检验规则文件是否改变越界行为。就已能量到的部分，结论是：规则文件是建议，门控才决定智能体实际能做什么。

  3. PyTorch：用 TorchTitan 在欧洲公共超算 JUPITER 上把约 1T MoE 预训练吞吐提高约 14 倍

    补入（原发布于 2026-11-12）。EUROPA 联合体（Domyn 与 Fraunhofer IAIS、IIS）介绍如何在于利希的 EuroHPC 超算 JUPITER 上，把约 1 万亿参数 MoE 的预训练做到可用吞吐。实验配置为总参数 951.9B、每 token 激活 32.8B，74 层、隐藏维度 6,144，384 个 routed expert 取 top-8，专家隐藏维度 1,792，词表 25.6 万，预训练序列长度 65,536，优化器为 Muon + AdamW。该机器是共享公共设施而非独占训练集群；每个数据并行副本用 384 块 GH200（96 个节点，每节点 4 颗 GH200）。通过 PyTorch 与 TorchTitan 的细粒度改动，每 GPU 吞吐从 90 token/s 提到约 1,300 token/s。文中点名的三项是：为 Muon 做的 FlexShard 放置以去掉大部分优化器通信；把 activation checkpoint 卸载到 Grace CPU；以及让 FSDP 的 all-gather 走计算流（unshard_async_op），每 GPU 约腾出 14 GiB HBM。相关改动已回馈 TorchTitan 和 PyTorch。

  4. PyTorch Helion 加入编译期启发式：不必长时间 autotune 也能接近调优后的速度

    补入（原发布于 2026-11-13）。Helion 是 PyTorch 的可移植内核 DSL，以往很依赖按内核、按 shape 的 autotune；文中举例，单个 paged-attention 内核在 72 个 shape 上，快速模式要 10 小时，全力模式要 25 小时。新的启发式在编译期读取内核 IR 和数据流，把内核分成 matmul、reduction 或 pointwise，直接给出 block size、warp 和 stage 等配置，分析本身只增加约数十毫秒。在 H100 上，覆盖 9 种线性注意力、96 个内核–shape 组合时，该配置前向比 Flash Linear Attention 手写 Triton 快 1.18 倍，含反向快 1.12 倍，并比 Helion 此前「不 autotune」的默认配置快 2.13 倍；在 vLLM 的 6 个生产 reduction 内核、153 个组合上，比 vLLM 自己的手写 CUDA/C++ 算子快 1.27 倍，比 Helion 原默认快 2.2 倍。作者强调这不是为了超过完整 autotune，而是在性能和等待时间之间给出一个可直接用的点。

  1. 在一块 GB10 上把 Inkling 2 Mini 的 vLLM 单请求解码调到 101 tok/s

    一篇实测笔记写了在 MSI EdgeXpert（一块 GB10、CPU/GPU 共享 128GB 内存）上为 Inkling 2 Mini 调 vLLM 的过程，上下文仍保持 131,072。作者给出：单请求 101 tok/s；4 路并发合计 195.7 tok/s；32K 提示的首 token 约 9.7 秒。在其对照的 Inkling 基准上，这是作者所知最快的单请求 vLLM 结果；同基准上 TensorFold 移植为 105.5 tok/s，一份 SGLang 配方为 112.0 tok/s。四路并发时，该配置超过了对照中已公布的两套结果。解码使用推测解码，草稿模型从随模型提供的 DSpark 换成 DFlash2，每步提议 7 个 token。调优时模型约占显存的 36%，机器上仍加载着闲置的 Qwen3.8-27B。

  2. Stable Gated DeltaNet-2：用对称擦除缓解线性注意力在长上下文训练中的状态爆炸

    Gated DeltaNet-2 为擦除和写入提供了独立的通道级控制，但在长上下文训练中会出现失败。作者将原因归于擦除时读、改方向不对称，使非正规擦除算子的增益沿 token 累积，即使没有新的写入也可能让状态指数增长。Stable GDN-2 改用对称擦除，保证状态传播非扩张，并用受衰减约束的残差写入保留写入灵活性；理论上给出循环状态增长的 O(√T) 上界，并保持分块并行计算。在 1.6B 模型上，循环设置的 128K RULER 平均分比 GDN-2 高 6.80 分；在混合设置的九项下游任务上平均准确率高 0.62 分。
